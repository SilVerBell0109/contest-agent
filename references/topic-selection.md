# topic-selection.md — 주제 정하기

## 1. 분야 선택 (공모 주제가 여러 개일 때) — 기준 4개
① 본인 역량과의 접점 ② 지원자가 몰릴 분야인지 ③ 학생에게 불리한 분야인지(영업 실무 등) ④ **취업 목표와 한 줄로 연결되는지**. 추천 1·차선 1을 내되, 사용자가 뒤집어도 된다(하나증권: 추천 3번 '안전한 금융', 선택 1번 '편리한 금융').

## 2. 후보 만들기 — 여덟 단계
1. 주최사 최근 6개월에서 실제 사건·숫자를 찾는다(org.md 연표).
2. 사람이 실제로 겪은 장면(인터뷰·판결·민원·팀원 경험)을 찾는다.
3. 문제의 크기를 숫자로 잰다. 가능하면 직접 센다("제가 세어 봤더니" + 조건).
4. 풀 수 없는 부분을 잘라 내고 경계를 문장으로 쓴다("복구는 전산팀이 할 일이고 이 아이디어는 손님이 보는 화면만", "매매 판단은 하지 않습니다", "대형 클라우드와 저장 용량을 두고 경쟁하지 않는다").
5. 왜 이 주최사·플랫폼이어야 하는지 한 단락으로, 주최사 자산을 기능에 엮는다("KIC라서 넣은 기능이 둘", "차량이라서 되는 것 넷", 손님톡·하나원큐).
6. 후보가 여럿이면 근거로 맞비교한다(설문·벤치마크). 약한 쪽은 확장으로 보낸다.
7. 시연 장면을 미리 정한다.
8. 컨셉을 한 문장으로("MTS가 멈춰도 손님의 주문은 멈추지 않는다").

사용자 고민 N개를 서비스 N개에 하나씩 대응시키는 방식도 쓴다(적립·투자·인출메이트).

## 3. 취업 목표 축 (사용자 기준)
후보를 "이 주제로 무엇을 시연하면 백엔드 면접에서 쓸 수 있는가"로 다시 본다. 엘리스에서 일상 아이디어 3개 → "직무 관련으로" → 모임 정산 에이전트(대사·멱등성·정합성). 참가 동기가 채용 혜택이면 그 혜택 조건(본선 10명, 최우수상)을 관문 가중치에 반영한다.

## 4. 중복 점검 — 두 축
- 기존 서비스: 기능별로 어디에 이미 있나 → 겹침/부분/없음. 해외 존재는 실현 가능성 근거로.
- 다른 지원자: 아이디어 유형별 몰림(높음/중간/낮음 추정). 주제 3 '안전한 금융'의 가장 흔한 답은 보이스피싱 FDS.
→ 겹치면 '주인공'을 바꾸고 나머지를 연동 기능으로 축소한다.

## 5. 수상 관문 비교 (KIC A/B에서 쓴 표)
후보를 심사 관문마다 "실패 확률"로 비교한다.

| 관문 | 물어볼 것 |
|---|---|
| 예선 상호평가(일반 참가자) | PDF 두 장을 비교해 직관적으로 고를 때 한 장으로 이해되는가 |
| 예선 전문가 — 실현 가능성 | 데이터가 전부 실제·공개인가, 합성 데이터 의심은 없는가 |
| 본선 구현 완성도 | 주어진 인원·기간에 안정적으로 도는 구조인가(파이프라인형이 테스트가 쉽다) |
| 본선 신뢰성 | 환각 대응을 실제로 보여 줄 수 있는가(원문 인용·이중 검증) |
| 발표·Q&A | 막아야 할 반박이 하나인가 둘인가 |
| 본인 역량 | 엔지니어링 비중 vs 도메인 학습 부담 |

추천 문장은 "아이디어가 더 좋아서가 아니라 수상까지 가는 관문에서 실패 확률이 낮아서". 이어서 "수상 확률을 더 올리는 조건 5~6개"(프레임 이름, 첫 장의 훅, 민감 쟁점 슬라이드 1장, 경쟁 도구 선제 대응표, 버린 후보를 확장 1순위로 흡수, 테스트 케이스 수 명시).
