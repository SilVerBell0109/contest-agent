# user-criteria.md — 사용자(최종은) 판단 기준

topic-strategist·judge-simulator·style-editor가 사용자 대신 판단할 때 쓰는 기준. 전부 실제 대화에서 사용자가 말했거나 선택으로 보여 준 것이다. 사용자가 직접 고쳐 쓴다.

## 1. 우선순위
1. **수상이 최우선.** 아이디어의 참신함보다 수상 관문에서의 실패 확률을 본다("무조건 수상을 하고싶은데", "수상권 상위 1%").
2. **취업 목표와 연결.** 금융권 백엔드(서버) 개발자, 2028 하반기 공채. 주제는 "이걸로 백엔드 면접에서 무엇을 보여 줄 수 있나"로 평가(대사·멱등성·정합성·동시성·DB). 채용 연계 혜택(서류 면제·필기 가산)은 참가 동기이자 관문 가중치.
3. 겹치지 않는 주제 — 기존 서비스와도, 다른 지원자와도.
4. 실현 가능성: 개인 참가면 기간 안에 혼자 안정적으로 돌릴 수 있는 파이프라인형. 데이터는 실제·공개.

## 2. 아이디어 평가 (광고·경험형에서 특히)
- 장소·메커니즘에 **개연성**이 있는가. 타깃이 그 순간 그런 심리 상태인가. 진짜 바이럴이 나는가.
- 머무는 곳 ○(페스티벌·한강), 이동 중인 곳 ×(지하철 환승), 혼잡·민원·안전 문제 ×.
- 브랜드 특정성: 아무 브랜드에나 붙는 아이디어는 기각.
- 실물 배출처럼 물류(냉동 유지)가 걸리면 뺀다.

## 3. 표현
- **AI 티 거부** — 문장·이미지·슬라이드 모두. 예시 문장 하나를 지목하는 방식으로 지적한다. 상투구·번역투·줄표·장식 배지·상담 말투·사족 캡션.
- 사족 제거. "프로젝트 외의 내용은 다 빼줘."
- 모르는 것은 모른다고 쓴다. 본인 경험이 없으면 밝히고 보도 사례로 대체.
- 본문은 합쇼체+1인칭. 양식이 개조식이면 개조식.

## 4. 협업 방식
- 판단은 본인이, 재료 수집은 위임("내가 판단할 수 있도록 자세한 조사"). 추천을 요청하면 단독 추천 + 이유를 원한다.
- 결과물은 **직접 읽고 고칠 수 있는 형태**(Google Doc·docx·붙여넣기용 txt). 마크다운 굵게·인용 태그가 섞인 텍스트는 싫어한다.
- 계획(plan.md) 승인 뒤 구현. 승인은 한 단어("전부 반영", "반영해줘", "오케이")로 온다 → 변경 로그에 그대로 적는다.
- 선택지는 짧게 번호로. 사용자는 번호로 답한다("1. 있음 2. 나중에 3. 모르겠음").
- 실질 마감을 공식 마감보다 앞에 둔다(알파: 7/31 vs 8/3).
- 허위 인용은 감점이므로 출처 검증이 먼저(컬잉 과제, 소마 "출처 없는 수치 금지").
- 여러 공모전을 같은 날 병행한다 → 작업 공간을 반드시 분리한다.

## 5. 프로필 (기획서 역량표·지원서에 쓸 사실만, 확인된 것)
- 국민대 소프트웨어학부(2023 입학), SW마에스트로 17기(팀 최고아웃풋, iOS·Android 앱 담당), WINK 동아리 프론트엔드.
- KOSCOM AI Agent Challenge 2025 우수상(코스콤 대표이사상) — 팀의 유일한 개발자, 은퇴 설계 MCP 서버 3종 설계·구현·배포.
- 제19회 ICT Award KOREA 2022 장려상(알고리즘), 제5회 국민대 알고리즘 대회 장려상.
- 스택: Swift/SwiftUI, Python, C++, React, Spring Boot 기초, Docker, MCP.
- 개인 참가 시 기본 가정: 1인 구현, 백엔드·데이터 파이프라인 강점, 금융 도메인 관심.
