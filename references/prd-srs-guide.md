# prd-srs-guide.md — PRD·SRS 작성과 단일 진실 원천

## 1. 역할
- **PRD**: 왜·누구·무엇(문제, 사용자, 유저플로우, 기능 우선순위, 성공 기준, 범위 밖, 리스크, 일정). 심사위원과 사용자가 읽는 말로.
- **SRS**: 어떻게(FR별 입력·처리·출력·예외·수용 기준, NFR, 데이터, 인터페이스, 사람/시스템 경계, 검증 계획, 개발 계획). 구현자가 읽는 말로.
- **traceability**: 심사 기준 ↔ PRD ↔ SRS ↔ E-ID ↔ 산출물 위치.

승인된 PRD·SRS가 **단일 진실 원천**이다. 이후 산출물(기획서·슬라이드·MVP·발표)은 이 안의 기능·수치·용어만 쓴다. 산출물을 만들다 새 기능·수치가 필요해지면 산출물에 끼워 넣지 말고 §변경 기록에 변경 요청을 적고 사용자 승인을 받은 뒤 스펙을 고친다.

## 2. 작성 규칙
1. 모든 사실에 E-ID. 근거 없는 수치 규칙은 [가정]으로 적고 "기각 피드백으로 조정" 같은 보정 경로를 둔다.
2. 유저플로우는 "끊김 없이 돌아야 하는 한 줄기"를 먼저 정하고(홈 → 진단 → 결과 → 비교 → 근거), 나머지는 목업으로 표시한다.
3. FR마다 수용 기준을 입력 → 기대 결과로 써서 테스트로 옮길 수 있게 한다(사용자 원칙 5: 성공 기준을 먼저 정의하고 실행).
4. 구현 상태 열(설계/구현중/구현완료/검증)을 두어 제출 시 완료와 계획을 구분한다.
5. 열린 질문은 "구현을 막지 않되 제출 전에 반드시 닫는다"로 관리한다(ZzaZan SRS 방식). 기한과 담당을 적는다.
6. 신뢰성 설계를 요구사항 단계에서 정의한다(ZzaZan 4축: 명시적 상태 전이, 멱등키+유일 제약, 삭제 순서 불변식과 주기적 조정, 민감 데이터 기기 전용 저장). 계산·판정은 결정적 코드, LLM은 인터페이스.
7. 비기능에 반드시: 개인정보 최소 수집·암호화·보관 기간, 시크릿은 .env, 라이선스 표, 데모 가용성(스냅샷·폴백).
8. 범위 밖을 명시한다(계좌개설 대행·실제 주문 실행·투자자문처럼 "하지 않는 것").
9. 버전과 변경 기록. 사용자 승인 문구("전부 반영", "승인")를 그대로 적는다.

## 3. 심사 기준 대응 절
traceability §1을 PRD 작성과 동시에 채운다. 심사 기준·✅ 질문마다 "어느 절이 답하는가"가 비면 PRD에 절을 추가한다(알파프로젝트: 선발 기준 4영역 각각에 정면 대응 문장).

## 4. 스펙에서 산출물로 가는 매핑
| 산출물 | PRD에서 가져오는 것 | SRS에서 가져오는 것 |
|---|---|---|
| 기획서·지원서 본문 | §1~§6, §7 기능(P0), §10, §11, §14 | §6 경계, §7 검증 계획 요약 |
| 슬라이드 12장 | 전부(장별 매핑은 templates/slides-12.md) | §1 구성, §2 FR 표, §5 인터페이스, §7, §8 |
| MVP 계획·코드 | §7 P0, §11 | FR·AC 전부, §8 개발 계획, §4 데이터 |
| 매뉴얼·README | §1, §6 | §5 인터페이스, §8 스택·배포 |
| 발표·시연 대본 | §1, §6.2 시나리오 | §7 검증 결과 수치 |
| 예상 질문 | §10 리스크 | §6 경계, §9 열린 질문 |

## 5. 승인 요청 방식
스펙을 다 쓴 뒤 사용자에게 보여 줄 것: 한 문장 정의, 유저플로우 한 줄기, P0 기능 표, 성공 기준 표, 범위 밖, 열린 질문. "이대로 진행할까요? 고칠 항목이 있으면 번호로 알려 주세요." 승인 문구를 CONTEST.md와 PRD §13에 기록한 뒤에만 `/contest:make`로 넘어간다.
